## 适用边界

- 循环 R = “机会到证据”；循环 S + 循环 E = “证据到部署”。
- 循环 E 的前提是公司已有最小交易平台；这里只定义单策略的接入、适配、验收和上线。
- 通用交易平台、数据库底座、实时风控、监控、事件响应和账务能力的从零建设，属于公司建设总图中的独立能力域，不得由某个策略任务重复建设。
- 本 SOP 不管理公司终态、阶段边界、资本配置、跨能力路线图或实时任务。

## 为什么量化公司的产研流程和互联网不一样

互联网公司的核心循环：**用户需求 → 产品设计 → 工程实现 → 上线**

量化公司的策略交付多了一个独特前置：**市场机制验证**——必须在策略接入工程开始前，用真实历史数据形成符合证据等级的结论，否则策略适配工程没有成立基础。

这是V4事故的根因之一：系统先建，策略后验证，两条线相互干扰。

**所以量化公司有三个串行循环（不可跳过、不可倒序）：**

```
循环R（研究验证）→ 循环S（策略规格化）→ 循环E（工程实现）
```

只有循环R通过后才进入循环S；循环S完成后才进入循环E。

互联网公司的需求分析/PRD/技术方案/测试/上线，在我们这里全部有对应物，但形态不同：

| 互联网环节 | 我们的对应物 | 阶段 |
|---|---|---|
| 需求分析 | 机制七问 + 机会地图 | 循环R起点 |
| 产品需求文档（PRD） | 预登记 + 策略规格书 | 循环R终点 / 循环S |
| 技术方案 | 策略接入设计 + 既有平台接口文档 | 循环E起点 |
| 数据库设计 | 策略字段映射 / 必要 Schema 变更 | 循环E |
| 接口文档 | 策略与平台的接口契约 | 循环E |
| 前端/后端开发 | 策略适配器与必要扩展开发（Codex） | 循环E |
| 测试 | 单元测试 + 纸面交易仿真 | 循环E |
| 上线 | 实盘部署 | 循环E出口 |
| 运营监控 | 日报 + 绩效归因 + L1/L2/L3审计 | 持续运营 |

## 循环R：研究验证（Research）

**定义：** 用历史数据证明"某个市场机制存在且可被捕捉"。输出一个PASSED的预登记研究结论。

**阶段门控（入口条件）：** 机会地图显示该方向处于Candidate或Conditional状态

### R1：机制立项

**具体任务：**
- 完成专业审查七问（CLAUDE.md §3），书面输出
- 更新机会地图（OPPORTUNITY_MAP_STATUS.md）
- 查GRAVEYARD_INDEX确认该机制未被否定

**交付物：** 七问审查memo（可以是对话记录截图或brief文档）

**验收标准（必须全部满足）：**
- [ ] 七问全部有实质性回答（不是"TBD"）
- [ ] 方向未被GRAVEYARD否定
- [ ] 机会地图状态已更新

**版本：** 不单独版本，归入任务书memo

---

### R2：数据可行性核查

**具体任务：**
- 确认目标资产/时间范围的数据可用性
- 计算样本量（触发事件数 n）
- MDE功效前置评估（β ≤ 0.20 at α = 0.05）
- 确认Holdout预留比例（每第5个事件预留）

**交付物：** `06_RESEARCH/RESULTS/YYYYMMDD_[策略名]_data_check.md`

**验收标准：**
- [ ] 数据时间范围确认（起止UTC时间戳）
- [ ] 预期事件数n明确
- [ ] 功效评估：以预期效应量计算β≤0.20的最小样本量，与n对比
- [ ] Holdout预留计划明确（事件级，非随机）

---

### R3：预登记（Research Preregistration）

**这是最重要的文档——等同于互联网公司的PRD，完成后不可修改**

**具体任务：**
- 冻结假设（可证伪命题）
- 冻结信号/触发定义（参数、分位数计算方式、样本截止）
- 冻结验收口径（v1.4四件套：E[R]>0、赢亏比、爆仓概率、几何增长）
- 冻结Episode合并规则
- 记录AI证据三行（来源/最可能错处/无多智能体共识偏差）

**交付物：** `06_RESEARCH/PREREGISTRATIONS/[策略名]_PREREG_v1.md`

**验收标准（进入回测的前提，缺一不进）：**
- [ ] 假设可证伪命题清晰（不是"可能有效果"）
- [ ] 触发定义完整，含分位数计算口径（禁全样本前视）
- [ ] 验收口径四件套明确列出，含seed
- [ ] Holdout物理隔离计划
- [ ] AI三行存在且真实（不是套话）
- [ ] 单变量（只有一个与基准不同的变量）

**文档版本规则：** `v1` = 预登记版（冻结，后续只能在 `v2+` 记录"修改了什么，为什么是错误"，不能改v1）

---

### R4：回测实现与验收

**具体任务：**
- Codex按预登记实现回测脚本
- Walk-Forward（WF）验证
- 成本完整性检查（手续费0.1%+滑点压力档0.3/0.5/1.0%+真实funding）
- 块bootstrap置信区间（seed与预登记一致）
- 五件套报告（四件套+第五件基准对照）

**交付物：**
- `06_RESEARCH/CODE/[策略名]_backtest.py`（可复跑，固定seed）
- `04_AI_TEAM/CODEX_TASKS/REPORT_[任务号].md`（Codex执行报告）

**验收标准：**
- [ ] 五件套全部报出（不只报Sharpe）
- [ ] WF轮次≥3，WF结论一致性高
- [ ] 成本三档压力测试完成
- [ ] pytest单测≥5项（含防前视、成本完整、样本隔离）
- [ ] 未读取Holdout

---

### R5：独立验收与归档

**具体任务（依失败计数状态）：**
- 普通结论：Claude独立验收，更新机会地图和GRAVEYARD/正向知识库
- 独立Alpha命数占用：Risk Reviewer盲审（Codex扮演独立评审）

**交付物（按结论）：**
- FAILED：`06_RESEARCH/GRAVEYARD_INDEX.md` 新增条目（含禁引用措辞）
- PASSED：`06_RESEARCH/GRAVEYARD_INDEX.md` 正向知识库条目 + 触发循环S

**循环R出口条件（同时满足）：**
- [ ] 五件套全部通过（含WF稳定性）
- [ ] Risk Reviewer未发现方法论缺陷
- [ ] 未动用Holdout

## 循环S：策略规格化（Strategy Specification）

**触发条件：** 循环R通过，机会地图状态升至Baseline/Confirmed

**定义：** 把研究结论翻译成工程可实现的策略规格——这是研究和系统之间的"翻译层"，互联网公司没有这层，量化公司必须有。

### S1：策略规格书

**具体任务：**
- 将回测中的信号/触发/持仓/退出规则翻译成确定性的伪代码或决策树
- 明确所有边界条件（同品种并发持仓、事件合并规则、时区统一）
- 明确与其他策略的交互规则（如A-1×Carry的优先级）

**交付物：** `06_RESEARCH/STRATEGY_SPECS/[策略名]_SPEC_v1.md`

**验收标准：**
- [ ] 规则可被工程师直接实现（无歧义）
- [ ] 所有参数数值明确（无"约X%"之类模糊）
- [ ] 边界条件全部覆盖
- [ ] 与预登记的信号定义完全一致（逐条对齐）

**文档版本规则：**
- `v1.0` = 从预登记翻译的初版
- `v1.x` = 工程实现期间的澄清修订（不得改信号逻辑）
- `v2.0` = 经过纸面交易验证后的修订版

---

### S2：成本与仓位模型规格

**具体任务：**
- 明确每次交易的成本计算公式（手续费taker/maker、预期滑点、funding结算时序）
- 定仓公式（认亏% × 止损距离 → 标准化合约数）
- 杠杆限制（杠杆是输出，不是输入）

**交付物：** 附于策略规格书S1，或单独 `COST_POSITION_MODEL_v1.md`

**验收标准：**
- [ ] 成本公式与回测代码完全一致
- [ ] 杠杆计算结果验证（手算一个样例对比）

---

### S3：验收测试规格（ATD）

**具体任务：**
- 定义系统实现正确性的可验证测试用例
- 基于已知输入数据，定义期望输出（持仓/P&L/风控触发）
- 定义纸面交易验收标准（跑N天，与回测信号一致率≥X%）

**交付物：** `06_RESEARCH/STRATEGY_SPECS/[策略名]_ATD_v1.md`（Acceptance Test Definition）

**验收标准：**
- [ ] ≥5个具体测试用例，含输入数据和期望输出
- [ ] 纸面交易通过标准明确（不是"运行正常"）

---

## 循环E：接入既有平台（Engineering Integration）

**触发条件：** 循环S全部完成，策略规格书FROZEN

**平台前提：** 公司最小交易平台及其通用风控、监控、状态和账务能力已经由公司级平台建设工作提供。若平台能力缺失，应回到 `COMPANY_BUILD_MASTERPLAN_v1.md` 管理该能力缺口，不得把“从零建设整个交易系统”塞入单策略循环 E。

### E1：策略接入架构设计

**参考既有平台文档：** `05_TECH_DESIGN/01_COMPANY_ORG.md`、`05_TECH_DESIGN/02_SYSTEM_ARCHITECTURE.md`

**具体任务：**
- 明确策略接入 Track A 确定性执行链的位置；Track B AI 分析不得进入下单权限链
- 明确策略适配器与既有平台各层的职责边界
- 画出该策略从信号到既有 Gateway 的数据流，不重画或重建公司平台

**验收标准：**
- [ ] 无歧义的层边界（哪个模块有权下单）
- [ ] AI分析层独立于执行链路（不阻塞、不绕过Gateway）
- [ ] 未为该策略复制订单、状态、风控、监控或账务底座
- [ ] 经Codex设计评审（DR机制）确认工程可行

---

### E2：策略数据映射与必要 Schema 变更

通用 PostgreSQL Schema 属于平台能力；本步骤只处理该策略接入所需的数据映射和最小兼容变更。

**具体任务：**
- 将策略规格中的信号、参数、状态和归因字段映射到既有业务表
- 如现有 Schema 无法表达，提出最小、向后兼容的变更
- 复核主键、索引、约束、写入者和读取者（单写原则）

**交付物：** 策略接入说明；如需公共变更，同步更新权威 `05_TECH_DESIGN/05_DB_SCHEMA.md`

**新增或变更字段的文档格式：**
```
表名：positions
用途：持仓记录，PostgreSQL是唯一权威状态源（DEC-008）
写入者：Decision Gateway（唯一）
读取者：Risk Check、报告层、AI Analyst（只读）

字段：
- trade_id: UUID, PK（DEC-010）
- symbol: VARCHAR(20)
- strategy: VARCHAR(50)
- opened_at_utc: TIMESTAMPTZ
- ...（完整字段列表）

索引：(symbol, opened_at_utc)
约束：status IN ('open', 'closed', 'force_closed')
```

**验收标准：**
- [ ] 策略所需字段均有权威落点，不另建影子状态源
- [ ] 单写原则：每张表只有一个模块有写权限
- [ ] 无内存字典（V4根因）——所有状态以DB为权威
- [ ] 与策略规格书中的数据需求完全对齐
- [ ] 公共 Schema 变更经平台级设计评审，不由单策略私自分叉

---

### E3：策略与平台接口契约

**具体任务：**
- 使用既有平台通信方式，定义策略适配器所需输入、输出、错误码和幂等性
- 明确进入 Decision Gateway 的条件和退出条件
- 对平台尚未提供的接口提出公共能力变更，不建立策略私有旁路

**交付物：** 策略接口契约；如需公共变更，同步更新权威 `05_TECH_DESIGN/06_MODULE_INTERFACE.md`

**验收标准：**
- [ ] 所有模块间接口都有明确契约
- [ ] 每个接口有错误处理定义
- [ ] 已标注哪些接口需要幂等性保证（订单执行类必须幂等）

---

### E4：策略适配开发（Codex任务分解）

**具体任务：**
- 按策略适配器或必要公共扩展分解 Codex 任务（每个任务≤一个模块，≤200行）
- 每个任务书包含：输出文件路径、验收标准、禁止项、TASK_INBOX写入步骤
- Claude按DR机制对高风险模块（Gateway/风控）做设计评审前置

**验收标准（每个模块）：**
- [ ] pytest单测覆盖（核心逻辑≥5项，覆盖错误路径）
- [ ] 日志可查（关键决策有结构化日志）
- [ ] 无内存字典持仓状态
- [ ] 与E2数据库设计完全对齐
- [ ] 未复制既有平台的交易、风险、监控或账务能力

---

### E5：平台集成测试与纸面交易

**具体任务：**
- 全链路集成测试（用历史数据"回放"驱动系统，验证持仓/P&L与回测结论吻合）
- 纸面交易（真实行情，虚拟资金，验证系统实际运行与策略规格书一致）
- 三方对账验证（交易所API / PostgreSQL / runtime state）

**验收标准（纸面交易通过门槛，见S3 ATD）：**
- [ ] 连续N天零系统报错
- [ ] 信号触发时序与策略规格书一致（逐笔对比）
- [ ] 三方对账差异为零
- [ ] AI分析层正常工作（日志可查，fallback正确触发）

---

### E6：策略实盘启用与运营接管

**触发条件：** E5通过，Founder D级批准

**具体任务：**
- 将策略部署到既有平台并启用最小资金档（DEC-015：1k档≤30%亏损阈值）
- 将策略纳入既有日报、周监控、月度轻量审计、异常响应和账务对账
- 若上述公共运营能力尚不存在，不得由策略项目临时复制；应回到公司能力建设路径补齐

## 文档版本标准（全项目统一）

### 版本号格式

`v{MAJOR}.{MINOR}`

- **MAJOR增加**：阶段跨越、假设重大修改、架构颠覆性变更
- **MINOR增加**：内容补充、澄清、错误修正、格式调整

**特殊版本：**
- `v1`（无小数）= 预登记类文档，冻结版，不得修改
- `vX.0-DRAFT` = 草稿状态
- `vX.0-FROZEN` = 冻结后不再修改

### 文档状态标签

每份文档头部必须有 **状态：** 字段，值为：

| 标签 | 含义 | 谁可以修改 |
|---|---|---|
| DRAFT | 起草中，未验收 | 作者 |
| REVIEW | 待挑战/验收 | 评审方可加批注 |
| FROZEN | 冻结，不再修改 | 仅阶段跨越后可解冻 |
| DEPRECATED | 已废弃，有替代版本 | 不修改，标注替代文档 |

## 变更记录格式（CHANGELOG）

**所有循环S和循环E的文档必须在末尾附CHANGELOG表。循环R文档用git history + DECISION_LOG代替。**

### CHANGELOG表格式

```markdown
## CHANGELOG

| 版本 | 日期 | 作者 | 变更内容 | 触发原因 |
|---|---|---|---|---|
| v1.0 | 2026-06-14 | Claude | 初版创建 | 研究R3通过，进入S阶段 |
| v1.1 | 2026-06-15 | Claude | 补充边界条件§3.2 | Codex实现发现信号定义有歧义 |
| v2.0 | 2026-07-01 | Claude | 全面修订（纸面交易验证后） | E5通过，更新实际参数 |
```

**变更记录规则：**
1. 每次改动必须新增一行，禁止覆盖写
2. 触发原因须来自实际事件（不写"优化"等模糊原因）
3. 若变更来自Codex的[专业异议]，触发原因注明"Codex DR异议：[异议主题]"
4. DEPRECATED文档的CHANGELOG最后一行记录废弃原因和替代文档
