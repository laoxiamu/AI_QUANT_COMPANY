## 为什么量化公司的产研流程和互联网不一样

互联网公司的核心循环：**用户需求 → 产品设计 → 工程实现 → 上线**

量化公司多了一个独特前置：**市场机制验证**——必须在工程开始前，用真实历史数据证明"这个策略有真实的盈利机制"，否则所有工程都是沙上建楼。

这是V4事故的根因之一：系统先建，策略后验证，两条线相互干扰。

**所以量化公司有三个串行循环（不可跳过、不可倒序）：**

```
循环R（研究验证）→ 循环S（策略规格化）→ 循环E（工程实现）
```

只有循环R通过后才进入循环S；循环S完成后才进入循环E。

互联网公司的需求分析/PRD/技术方案/测试/上线，在我们这里全部有对应物，但形态不同：

| 互联网环节 | 我们的对应物 | 阶段 |
|---|---|---|
| 需求分析 | 机制七问 + 机会地图 | 循环R起点 |
| 产品需求文档（PRD） | 预登记 + 策略规格书 | 循环R终点 / 循环S |
| 技术方案 | 系统架构图 + 模块接口文档 | 循环E起点 |
| 数据库设计 | PostgreSQL Schema设计 | 循环E |
| 接口文档 | 模块接口契约 | 循环E |
| 前端/后端开发 | 交易系统开发（Codex） | 循环E |
| 测试 | 单元测试 + 纸面交易仿真 | 循环E |
| 上线 | 实盘部署 | 循环E出口 |
| 运营监控 | 日报 + 绩效归因 + L1/L2/L3审计 | 持续运营 |

## 循环R：研究验证（Research）

**定义：** 用历史数据证明"某个市场机制存在且可被捕捉"。输出一个PASSED的预登记研究结论。

**阶段门控（入口条件）：** 机会地图显示该方向处于Candidate或Conditional状态

### R1：机制立项

**具体任务：**
- 完成专业审查七问（CLAUDE.md §3），书面输出
- 更新机会地图（OPPORTUNITY_MAP_STATUS.md）
- 查GRAVEYARD_INDEX确认该机制未被否定

**交付物：** 七问审查memo（可以是对话记录截图或brief文档）

**验收标准（必须全部满足）：**
- [ ] 七问全部有实质性回答（不是"TBD"）
- [ ] 方向未被GRAVEYARD否定
- [ ] 机会地图状态已更新

**版本：** 不单独版本，归入任务书memo

---

### R2：数据可行性核查

**具体任务：**
- 确认目标资产/时间范围的数据可用性
- 计算样本量（触发事件数 n）
- MDE功效前置评估（β ≤ 0.20 at α = 0.05）
- 确认Holdout预留比例（每第5个事件预留）

**交付物：** `06_RESEARCH/RESULTS/YYYYMMDD_[策略名]_data_check.md`

**验收标准：**
- [ ] 数据时间范围确认（起止UTC时间戳）
- [ ] 预期事件数n明确
- [ ] 功效评估：以预期效应量计算β≤0.20的最小样本量，与n对比
- [ ] Holdout预留计划明确（事件级，非随机）

---

### R3：预登记（Research Preregistration）

**这是最重要的文档——等同于互联网公司的PRD，完成后不可修改**

**具体任务：**
- 冻结假设（可证伪命题）
- 冻结信号/触发定义（参数、分位数计算方式、样本截止）
- 冻结验收口径（v1.4四件套：E[R]>0、赢亏比、爆仓概率、几何增长）
- 冻结Episode合并规则
- 记录AI证据三行（来源/最可能错处/无多智能体共识偏差）

**交付物：** `06_RESEARCH/PREREGISTRATIONS/[策略名]_PREREG_v1.md`

**验收标准（进入回测的前提，缺一不进）：**
- [ ] 假设可证伪命题清晰（不是"可能有效果"）
- [ ] 触发定义完整，含分位数计算口径（禁全样本前视）
- [ ] 验收口径四件套明确列出，含seed
- [ ] Holdout物理隔离计划
- [ ] AI三行存在且真实（不是套话）
- [ ] 单变量（只有一个与基准不同的变量）

**文档版本规则：** `v1` = 预登记版（冻结，后续只能在 `v2+` 记录"修改了什么，为什么是错误"，不能改v1）

---

### R4：回测实现与验收

**具体任务：**
- Codex按预登记实现回测脚本
- Walk-Forward（WF）验证
- 成本完整性检查（手续费0.1%+滑点压力档0.3/0.5/1.0%+真实funding）
- 块bootstrap置信区间（seed与预登记一致）
- 五件套报告（四件套+第五件基准对照）

**交付物：**
- `06_RESEARCH/CODE/[策略名]_backtest.py`（可复跑，固定seed）
- `04_AI_TEAM/CODEX_TASKS/REPORT_[任务号].md`（Codex执行报告）

**验收标准：**
- [ ] 五件套全部报出（不只报Sharpe）
- [ ] WF轮次≥3，WF结论一致性高
- [ ] 成本三档压力测试完成
- [ ] pytest单测≥5项（含防前视、成本完整、样本隔离）
- [ ] 未读取Holdout

---

### R5：独立验收与归档

**具体任务（依失败计数状态）：**
- 普通结论：Claude独立验收，更新机会地图和GRAVEYARD/正向知识库
- 独立Alpha命数占用：Risk Reviewer盲审（Codex扮演独立评审）

**交付物（按结论）：**
- FAILED：`06_RESEARCH/GRAVEYARD_INDEX.md` 新增条目（含禁引用措辞）
- PASSED：`06_RESEARCH/GRAVEYARD_INDEX.md` 正向知识库条目 + 触发循环S

**循环R出口条件（同时满足）：**
- [ ] 五件套全部通过（含WF稳定性）
- [ ] Risk Reviewer未发现方法论缺陷
- [ ] 未动用Holdout

## 循环S：策略规格化（Strategy Specification）

**触发条件：** 循环R通过，机会地图状态升至Baseline/Confirmed

**定义：** 把研究结论翻译成工程可实现的策略规格——这是研究和系统之间的"翻译层"，互联网公司没有这层，量化公司必须有。

### S1：策略规格书

**具体任务：**
- 将回测中的信号/触发/持仓/退出规则翻译成确定性的伪代码或决策树
- 明确所有边界条件（同品种并发持仓、事件合并规则、时区统一）
- 明确与其他策略的交互规则（如A-1×Carry的优先级）

**交付物：** `06_RESEARCH/STRATEGY_SPECS/[策略名]_SPEC_v1.md`

**验收标准：**
- [ ] 规则可被工程师直接实现（无歧义）
- [ ] 所有参数数值明确（无"约X%"之类模糊）
- [ ] 边界条件全部覆盖
- [ ] 与预登记的信号定义完全一致（逐条对齐）

**文档版本规则：**
- `v1.0` = 从预登记翻译的初版
- `v1.x` = 工程实现期间的澄清修订（不得改信号逻辑）
- `v2.0` = 经过纸面交易验证后的修订版

---

### S2：成本与仓位模型规格

**具体任务：**
- 明确每次交易的成本计算公式（手续费taker/maker、预期滑点、funding结算时序）
- 定仓公式（认亏% × 止损距离 → 标准化合约数）
- 杠杆限制（杠杆是输出，不是输入）

**交付物：** 附于策略规格书S1，或单独 `COST_POSITION_MODEL_v1.md`

**验收标准：**
- [ ] 成本公式与回测代码完全一致
- [ ] 杠杆计算结果验证（手算一个样例对比）

---

### S3：验收测试规格（ATD）

**具体任务：**
- 定义系统实现正确性的可验证测试用例
- 基于已知输入数据，定义期望输出（持仓/P&L/风控触发）
- 定义纸面交易验收标准（跑N天，与回测信号一致率≥X%）

**交付物：** `06_RESEARCH/STRATEGY_SPECS/[策略名]_ATD_v1.md`（Acceptance Test Definition）

**验收标准：**
- [ ] ≥5个具体测试用例，含输入数据和期望输出
- [ ] 纸面交易通过标准明确（不是"运行正常"）

## 循环E：工程实现（Engineering）

**触发条件：** 循环S全部完成，策略规格书FROZEN

### E1：系统架构设计

**已有文档：** `05_TECH_DESIGN/01_COMPANY_ORG.md`、`05_TECH_DESIGN/02_SYSTEM_ARCHITECTURE.md`（E2，待完成）

**具体任务：**
- 双轨制架构图（Track A确定性执行 / Track B AI分析）
- 各层职责边界明确
- 数据流向图（信号如何流转到下单）

**验收标准：**

- [ ] 经Codex设计评审（DR机制）确认工程可行

---

### E2：PostgreSQL数据库设计

**这是v1缺失的关键环节**

**具体任务：**
- 设计所有业务表（持仓、订单、信号、风控日志、AI分析日志、对账记录）
- 明确主键策略、索引、约束
- 明确每张表的写入者和读取者（单写原则）

**交付物：** `05_TECH_DESIGN/05_DB_SCHEMA.md`

**文档格式（每张表必须包含）：**
```
表名：positions
用途：持仓记录，PostgreSQL是唯一权威状态源（DEC-008）
写入者：Decision Gateway（唯一）
读取者：Risk Check、报告层、AI Analyst（只读）

字段：
- trade_id: UUID, PK（DEC-010）
- symbol: VARCHAR(20)
- strategy: VARCHAR(50)
- opened_at_utc: TIMESTAMPTZ
- ...（完整字段列表）

索引：(symbol, opened_at_utc)
约束：status IN ('open', 'closed', 'force_closed')
```

**验收标准：**
- [ ] 所有业务表完整定义
- [ ] 单写原则：每张表只有一个模块有写权限
- [ ] 无内存字典（V4根因）——所有状态以DB为权威
- [ ] 与策略规格书中的数据需求完全对齐

**这是v1缺失的关键环节**

- 对每个接口：输入类型、输出类型、错误码、幂等性要求

**交付物：** `05_TECH_DESIGN/06_MODULE_INTERFACE.md`

**验收标准：**

- [ ] 每个接口有错误处理定义
- [ ] 已标注哪些接口需要幂等性保证（订单执行类必须幂等）

### E5：集成测试与纸面交易

## 文档版本标准（全项目统一）

### 版本号格式

`v{MAJOR}.{MINOR}`

- **MAJOR增加**：阶段跨越、假设重大修改、架构颠覆性变更
- **MINOR增加**：内容补充、澄清、错误修正、格式调整

**特殊版本：**
- `v1`（无小数）= 预登记类文档，冻结版，不得修改
- `vX.0-DRAFT` = 草稿状态
- `vX.0-FROZEN` = 冻结后不再修改

### 文档状态标签

每份文档头部必须有 **状态：** 字段，值为：

| 标签 | 含义 | 谁可以修改 |
|---|---|---|
| DRAFT | 起草中，未验收 | 作者 |
| REVIEW | 待挑战/验收 | 评审方可加批注 |
| FROZEN | 冻结，不再修改 | 仅阶段跨越后可解冻 |
| DEPRECATED | 已废弃，有替代版本 | 不修改，标注替代文档 |

## 变更记录格式（CHANGELOG）

**所有循环S和循环E的文档必须在末尾附CHANGELOG表。循环R文档用git history + DECISION_LOG代替。**

### CHANGELOG表格式

```markdown
## CHANGELOG

| 版本 | 日期 | 作者 | 变更内容 | 触发原因 |
|---|---|---|---|---|
| v1.0 | 2026-06-14 | Claude | 初版创建 | 研究R3通过，进入S阶段 |
| v1.1 | 2026-06-15 | Claude | 补充边界条件§3.2 | Codex实现发现信号定义有歧义 |
| v2.0 | 2026-07-01 | Claude | 全面修订（纸面交易验证后） | E5通过，更新实际参数 |
```

**变更记录规则：**
1. 每次改动必须新增一行，禁止覆盖写
2. 触发原因须来自实际事件（不写"优化"等模糊原因）
3. 若变更来自Codex的[专业异议]，触发原因注明"Codex DR异议：[异议主题]"
4. DEPRECATED文档的CHANGELOG最后一行记录废弃原因和替代文档
