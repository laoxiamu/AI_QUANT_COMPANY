# BPR 方法对公司顶层框架的适用性评审

**日期：** 2026-06-15
**性质：** 外部方法参考，不构成项目决策，不直接修改现有公司 OS
**面向：** Claude（项目主理人 / CTO）
**来源：** 微信公众号《从职能分工到端到端价值重构：业务流程再造（BPR）的方法体系与实践路径》
**原文：** https://mp.weixin.qq.com/s/zR1R_Kiw_BmYX6eiFOcjSw

---

## 1. 给 Claude 的直接结论

Founder 对 `OPERATING_MODEL_DESIGN_v2` 的批评成立：它主要描述“单策略从研究到工程”的生产线，不能承担公司级运营模型或项目总计划的职责。

Claude 提出的 9 个工作流基本覆盖了公司所需能力，但仍需一次结构纠正：

> **9 项应定义为“能力域”，不能直接等同于 9 条端到端流程。**

如果只把研究、系统、风控、监控、账务、治理、项目管理分别列成九块，仍可能重复传统职能制的问题：每块内部很完整，跨块交付无人负责。顶层框架需要同时存在两张正交地图：

1. **能力地图：** 公司必须具备什么能力。
2. **端到端价值流：** 一个业务结果如何跨能力域完成，以及谁对最终结果负责。

因此，不建议直接把 9 工作流写成一份更大的 `OPERATING_MODEL_v3`。应先建立稳定的公司建设总图，再把策略生产线降级为其中一条 SOP。

---

## 2. 原文方法的核心内容

文章的主张可压缩为五点：

1. 管理单元应从“部门任务”切换为“端到端业务结果”。
2. 先建立企业级流程全景，再拆局部流程，避免局部优化。
3. 流程架构分层：L1 企业价值链，L2-L3 流程域与场景，L4-L5 执行细则。
4. 流程优先级由战略重要性、改进空间、变革准备度共同决定。
5. 流程必须同时具备输入、活动、角色、规则/数据、输出/绩效，并由流程所有者持续运营。

文章还给出“七个 R”重构视角：Rethink、Reconfigure、Reassign、Resequence、Relocate、Reduce、Retool。

证据边界：本评审读取了文章正文；文末展示的 64 页案例以图片形式出现，本次未把图片案例内容作为证据。

## 3. 对本项目最有价值的迁移

### 3.1 先画 L1 公司价值流，不先列任务

当前项目的根本缺口不是“少了一张任务表”，而是没有稳定回答：

- 公司通过哪些端到端过程创造价值？
- 每条过程的起点、终点和结果是什么？
- 哪些能力域参与？
- 谁对最终结果负责？

建议的 L1 价值流：

| L1 价值流 | 起点 | 终点 | 主要结果 |
|---|---|---|---|
| **机会到证据** | 市场机制机会 | 可审计的通过/否定结论 | 识别真实 edge，诚实淘汰伪机会 |
| **证据到部署** | 已通过研究结论 | 可受控运行的策略实例 | 把 edge 变成可验证产品 |
| **信号到结算** | 市场状态/策略信号 | 成交、持仓、账务一致 | 安全执行并形成真实 PnL |
| **异常到恢复** | 风险/技术异常 | 风险受控、状态恢复、事故闭环 | 保住资本与系统可信度 |
| **绩效到配置** | 实盘绩效与风险证据 | 继续、缩减、暂停或增配资本 | 动态管理两层资本 |
| **决策到交付** | 公司级目标/问题 | 经验收的里程碑 | 管理跨模块建设与资源优先级 |
| **结果到知识** | 研究、交易、事故结果 | 可复用知识和规则更新 | 防止重复犯错与叙事污染 |

这些价值流会横跨 Claude 提出的 9 个能力域。例如“证据到部署”会同时经过策略规格、交易系统、风控、监控、账务、治理，而不是归属于某一个模块。

### 3.2 9 项重命名为公司能力域

Claude 当前的 9 项拆解可保留并稍作调整：

| 能力域 | 定位 |
|---|---|
| 战略、目标函数与资本边界 | 顶层约束，不是普通任务流 |
| Alpha 研究与证据管理 | 发现和证伪 edge |
| 策略产品化 | 将研究结论转成确定性规格与验收定义 |
| 交易平台与数据基础设施 | 被所有策略复用的产品能力 |
| 实时风险与资本保护 | 公司生存、账户、策略、单笔多层防线 |
| 交易运营、监控与事件响应 | 日常运行、告警、处置、恢复 |
| 资本、账务与绩效归因 | 配置、对账、PnL、成本、税务资料 |
| 治理、知识与审计 | 决策、证据、墓园、复现、权限 |
| 项目组合与交付管理 | 路线图、依赖、里程碑、预算和状态 |

这里将“监控告警”并入交易运营，将“策略规格化”保留为独立能力域。原因是监控不是独立创造价值的孤岛，而是运行和事件响应的一部分；策略产品化则是研究与平台之间不可省略的翻译层。

### 3.3 每条价值流指定单一结果责任人

文章的“流程所有者”思想适用，但本项目不能照搬多人公司的岗位体系。Owner 应是**责任帽子**而非新增组织层级：

| 价值流 | 建议 Accountable |
|---|---|
| 机会到证据 | Claude / Quant Research Lead |
| 证据到部署 | Claude / Product Owner；Codex 对实现负责 |
| 信号到结算 | 确定性交易控制器；Claude 对设计验收负责 |
| 异常到恢复 | Claude / Risk & Operations Lead；资金动作升 Founder |
| 绩效到配置 | Founder 决策，Claude 提交证据化建议 |
| 决策到交付 | Claude / Operating Principal |
| 结果到知识 | Claude 对语义负责，Codex 可执行整理与校验 |

单一责任人不等于单一执行者。Codex 可以承担大量实现，但不应成为方向与资本结果的 Accountable。

## 4. 项目级文档应如何分层

不建议创造一份包揽战略、架构、路线图、任务和 SOP 的巨型文件。建议建立四层：

| 层级 | 文档职责 | 更新频率 |
|---|---|---|
| **公司建设总图** | 终态、能力地图、L1价值流、阶段成熟度、全局依赖 | 低频 |
| **项目组合路线图** | 各能力域阶段目标、里程碑、依赖、预算、优先级 | 月度/重大变化 |
| **实时任务台账** | 进行中、待执行、完成、废弃、阻塞 | 持续；可继续使用 `CURRENT_STATE §4` |
| **流程 SOP / 规格** | 策略生产线、事故响应、部署、对账等具体执行规则 | 按版本 |

建议的新项目级主文档可命名为：

`00_PROJECT_MANAGEMENT/COMPANY_BUILD_MASTERPLAN_v1.md`

它应回答：

1. 公司终态是什么。
2. 有哪些能力域和端到端价值流。
3. 每个能力当前成熟度是什么。
4. 分几个建设阶段，每阶段的出口条件是什么。
5. 跨能力域依赖和关键路径是什么。
6. 哪些模块已完成、在建、待建、废弃。
7. 实时状态去哪里读取，而不是在主文档重复维护。

`OPERATING_MODEL_DESIGN_v2` 建议重定位并改名为：

`STRATEGY_DELIVERY_LIFECYCLE_SOP_v1`

其 R-S-E 结构仍有价值，但应表达为“机会到证据 + 证据到部署”的局部流程，循环 E 只覆盖**策略接入既有平台**，不再包含“从零建设整个交易系统”。

## 5. 优先级方法的项目化改造

文章的三维筛选可以采用，但应改写为量化公司版本：

| 维度 | 本项目问题 |
|---|---|
| 战略价值 | 是否直接增加 edge 发现能力、资本安全或可运营性？ |
| 风险/缺口 | 当前缺失是否会导致资金损失、错误结论或阶段阻塞？ |
| 依赖解锁 | 完成后能解锁多少后续价值流或里程碑？ |
| 证据与准备度 | 数据、规格、人员/Agent、基础设施是否足以实施？ |
| 成本与可逆性 | 时间、资金、复杂度多大；错误后是否容易回退？ |

建议优先级不是简单总分，而是先过硬门：

1. 资本安全和数据真实性缺口优先。
2. 当前阶段关键路径优先。
3. 能复用、能解锁多条价值流的平台能力优先。
4. 纯美化、低复用、无明确出口条件的治理建设后置。

这能避免 BPR 被误用成新一轮治理扩张。

## 6. “七个 R”的适用方式

七个 R 适合作为设计评审清单，不适合变成每个任务强制填写的表格：

| R | 本项目示例 |
|---|---|
| Rethink | 为什么每个策略都要重复定义工程系统？ |
| Reconfigure | 将通用交易平台从单策略工程阶段抽离 |
| Reassign | Claude 负责方向和验收，Codex 负责实现，不让 Founder 搬运技术选择 |
| Resequence | 先数据适用性/功效，再预登记和计算密集型实验 |
| Relocate | 把账户状态放入 DB，把跨会话状态放入权威文件 |
| Reduce | 减少重复审计、重复状态记录和无信息增益文档 |
| Retool | 用事件驱动任务收件箱、自动状态校验和 IM 控制面降低人工搬运 |

建议只在以下情况调用七个 R：跨能力域卡顿、重复失败、事故复盘、阶段转换、流程周期显著超标。

## 7. 不应照搬的传统 BPR 内容

1. **不引入 ARIS 或重型企业架构工具。** 当前规模下 Markdown + Mermaid + 状态校验足够。
2. **不建立部门和岗位绩效体系。** 一人公司应管理结果、状态和证据，不制造虚拟官僚层级。
3. **不做大爆炸式流程再造。** 先建立 L1/L2 地图，再选择关键价值流逐条落地。
4. **不把所有规则立即系统固化。** 原则层冻结，运行层保持 v0.x 迭代，与现有 DEC-069 一致。
5. **不以文档完成率衡量进展。** 核心指标应是交付周期、证据质量、事故率、状态一致性和资本结果。

## 8. 对 Claude 当前 9 工作流方案的校准意见

**结论：框架方向正确，但不能直接进入详细任务拆解。**

在编写公司建设总图前，建议 Claude 先完成三个修正：

1. 把 9 项从“工作流”改称“能力域”。
2. 在能力域之上补 L1 端到端价值流，并定义每条流的输入、输出、Owner、指标和参与能力。
3. 将文档体系拆成“总图、路线图、实时台账、SOP”四层，避免新的总计划书再次因承载过多职责而失效。

完成这三项后，Claude 可以自主起草 `COMPANY_BUILD_MASTERPLAN_v1.md`，再由 Founder 对终态范围、阶段边界和重大资本/架构事项做 D 级确认。

## 9. 建议的最小落地顺序

1. 重定位 `OPERATING_MODEL_DESIGN_v2`，保留内容但停止将其视为公司总模型。
2. 产出一页 L1 价值流图与一页能力地图，先检查是否覆盖整个公司。
3. 建立能力域 × 价值流矩阵，识别无人负责、重复建设和关键依赖。
4. 起草公司建设总图，只写阶段与里程碑，不塞入具体任务。
5. 继续以 `CURRENT_STATE §4` 管理实时任务，避免双账本。
6. 选“决策到交付”或“证据到部署”做一次最小试运行，再冻结模板。

**专业判断：** 当前最大的风险不是顶层设计不够精美，而是再次把“写完整框架”做成一个长期治理项目。总图应足够完整地防止错层，同时足够轻，能尽快回到 carry 研究、采集器和生产能力建设。
