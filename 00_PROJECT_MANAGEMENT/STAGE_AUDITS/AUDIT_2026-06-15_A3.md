# AUDIT 2026-06-15 A3：风控 + 资本 + 合规 + 运营

**棱镜：** 别亏光、别出事、能持续运营  
**执行日期：** 2026-06-19 UTC  
**结论：** CONDITIONAL NO-GO FOR REAL MONEY。研究治理已经够硬，但生产交易的“活下来”能力尚未建成。任何真实资金上线前，必须先完成最小实时风控、账务对账、运营接管和合规/对手方底线。小额不能豁免这些能力，只能降低实现深度。

本审计未读取 Holdout；未参考其他 A1/A2/A4 独立审计结论作为论据。外部合规信息仅作风险识别，不构成法律或税务意见。

## 一、最高风险判断

项目最可能“非因策略失败而归零”的路径不是单笔亏损，而是：**交易所/账户/API/运营事故穿透两层资本，且没有实时阻断、对账和人工接管链。**

当前文档已经知道这个问题，但项目低估了它的上线阻断级别：

- `COMPANY_BUILD_MASTERPLAN_v1.md` 明确交易平台、实时风控、资本账务为“草图”，交易运营/监控/事件响应为“空白”。
- `05_TECH_DESIGN/04_MODULE_DESIGN.md` 明确 Execution System 未建设，P0 阻塞项是 Decision Gateway + Risk Engine + Position Registry。
- `PROJECT_TASK_PLAN.md` 中 P1-RISK、P1-OPS、P1-ACC 仍基本待办。
- `REPORT_E4.md` 已指出 Phase 2 风控参数来源存在审计断点；DEC-072 也承认关键参数仍是 DRAFT，代码化前须另立 DEC 冻结。

所以：**实时风控只有规则、无代码，是实盘前致命缺口。**

## 二、发现清单

### 1. 致命：两层资本现在是治理概念，不是资金隔离

**问题：** DEC-063/069 的核心资本/围栏资本设计方向正确，但如果资金仍在同一交易所账户、同一 cross wallet、同一 API key、同一自动转账权限下，围栏“可归零”会穿透核心资本。特别是 carry v4 使用 Binance spot + USDT-M cross margin，若账户级抵押、自动补款、API 权限或人工误操作没有物理边界，核心保护只是文档。

**证据：**
- DEC-063：核心资本受保护、围栏子账户可归零。
- DEC-069：围栏证据等级解锁，10k 档起启用。
- `CARRY_DELTA_NEUTRAL_PREREG_v4.md`：Binance spot + USDT-M cross margin；B/E/M 内部转账、补款、强平路径均需精确账本。
- `PROJECT_TASK_PLAN.md`：资金划转审批与审计记录 P1-ACC-005 仍待办。

**更优方案：** 实盘前冻结“资金物理隔离协议”：

1. 核心资本绝大部分不放交易所，保留在银行/低风险钱包；交易所只放本轮批准额度。
2. 围栏账户使用独立子账户或独立交易所账户；API key、保证金模式、转账权限与核心隔离。
3. API key 禁用提现；只允许白名单 IP；交易权限按策略最小化。
4. 禁止自动从核心向围栏补款；任何补血必须 Founder D 级确认并入账。
5. 真实资金上线初期，单交易所托管资产上限建议不超过项目总本金 30%-40%，超限必须重审。

**谁决策：** Founder D 级冻结资金边界；Claude 定义协议；Codex 实现权限检查和对账。

### 2. 致命：Decision Gateway / Risk Engine / Position Registry 未实现，不能小额实盘

**问题：** 当前项目已经有正确的风控原则：PostgreSQL 权威、禁止内存状态、Reconciliation、Orphan Detection、Gateway 唯一下单。但这些仍是设计和任务，不是运行能力。小额实盘时，最大事故不是亏 300 元，而是状态漂移、重复单、漏平仓、API 错误或强平后现货裸露。

**证据：**
- DEC-008~011 来自 Ghost Position 事故：DB 权威、禁止同向覆盖、trade_id、Reconciliation/Orphan Detection。
- `PROJECT_CONTEXT.md`：历史 Ghost Position 造成持仓从风控中消失，ETH 实际亏损 -5.47%，BTC -2.35%，49 笔僵尸持仓。
- `05_TECH_DESIGN/02_SYSTEM_ARCHITECTURE.md`：Decision Gateway 代码化待 Phase 2。
- `05_TECH_DESIGN/04_MODULE_DESIGN.md`：Execution System 未建设。
- `PROJECT_TASK_PLAN.md`：P1-RISK-002~006 全部待办。

**更优方案：最小可行实时风控（MVR）**

必须在 paper 环境先实现并通过故障注入，才能接真实资金：

1. **单一下单入口：** `decision_requests -> risk_decisions -> orders`，策略只能写 request，不能碰交易 API。
2. **DB 权威持仓：** `positions/trades/orders/account_snapshots/risk_checks` 五张最小表；所有对象有 `trade_id`、`order_id`、幂等键、状态机。
3. **Pre-trade 硬门：** 账户额度、策略额度、单资产额度、重复同向持仓、最大认亏额、强平价距、事件窗、数据新鲜度。
4. **Post-trade 对账：** 每次成交后立即拉交易所订单/成交/持仓，与 DB 对账；差异非零进入 `BLOCK_NEW_ORDERS`。
5. **周期风险扫描：** 至少每 5 分钟检查交易所持仓、DB 持仓、runtime cache；任何孤儿持仓或未检查超时立即告警并禁止新开仓。
6. **Kill switch：** 本地文件开关 + DB flag + 交易所全撤单/减仓脚本；演练过才算存在。
7. **测试门：** 重复请求、部分成交、断网、DB 延迟、交易所返回不一致、重启恢复、强平后现货裸露、API timeout 全部有测试。

**谁决策：** CTO 冻结 MVR 技术门；Codex 实现；Founder 只批真实资金启用。

### 3. 重大：DEC-015 本金阶梯合理，但“认亏%”必须从账户层改成订单级损失上限

**问题：** DEC-015 的 1k/10k/30k 最大亏损阈值合理，绝对亏损递增、比例递减。但目前容易被误用为“账户亏到阈值再停”。实盘风控必须把阈值拆成订单级、日级、策略级和账户级硬限制。尤其永续合约中，“杠杆=输出非输入”只有在每单强平价距、滑点压力、止损失败路径都计算后才成立。

**证据：**
- DEC-015：1,000 元最大亏损 300；10,000 元最大亏损 1,000；30,000 元最大亏损 1,500。
- DEC-019：永续必须建模 funding 与强平；任一强平为重大事故。
- DEC-072：单日 -2%、总回撤 -20%、事件窗等仍为 DRAFT。
- `PHASE1_RESEARCH_THESIS_v1.md`：杠杆只表达风控计算结果，不是目标。

**更优方案：** 资金协议中冻结四层硬门：

- 单笔：最大可亏 = 账户 NAV 的 0.25%-0.50%，且按保守滑点后仍不超过。
- 日级：达到 -1% 预警，-2% 禁止新开仓并只允许降风险。
- 策略级：达到该策略月度亏损预算即暂停，不用账户总亏损兜底。
- 账户级：达到 DEC-015 档位亏损立即停机复盘；不是“还可以继续试”。

**谁决策：** Founder D 级冻结参数；Claude 形成协议；Codex 在 Gateway 中硬编码。

### 4. 重大：账务/对账不能手工扛过；税务资料可以先半手工，但账本必须先建

**问题：** 3 万本金下，完整财务系统不值得重建企业 ERP；但订单、成交、funding、fee、PnL、NAV、出入金、内部划转的最小账本必须先建。小额实盘中最容易亏掉的不是策略，而是解释不了真实 PnL、把内部转账当收益、漏计 funding/fee、交易所和本地状态不一致。

**证据：**
- `COMPANY_BUILD_MASTERPLAN_v1.md`：资本、账务与绩效归因为草图；缺口包括生产账本 schema、交易所账单导入、日结/月结、差异处理、税务归档。
- `PROJECT_TASK_PLAN.md`：P1-ACC-001~005 均待办。
- carry v4 已经把 USDT NAV、funding、fee、强平、负债、basis 归因做成严格账本，说明项目知道复杂度。

**更优方案：**

必须先建：
- `ledger_entries` 双分录或准双分录账本；
- `exchange_statements_raw` 原始交易所账单归档；
- 每日 UTC NAV snapshot；
- 交易所/DB/runtime 三方对账；
- PnL 分解：price、funding、fee、slippage、transfer、liquidation、residual。

可临时手工：
- 月度税务汇总；
- 出入金凭证归档；
- 年度报税材料整理。

但前提是原始账单、链上/银行/交易所出入金记录、每日 NAV 与成交明细已经自动归档。没有这些，税务也无法可靠手工补。

**谁决策：** CTO 冻结账本 schema；Codex 实现；Founder 确认税务顾问/申报路径。

### 5. 重大：合规与对手方风险被识别过，但未进入阶段门

**问题：** 项目文档零散提到交易所风险、账户冻结、政策变化、API key，但目前没有形成上线前硬门。对于“中国身份 + 境外交易所 + 永续合约”的组合，最大非市场风险包括：平台限制服务、KYC/地址/居住地变更、出入金通道受阻、账户风控冻结、交易所破产或暂停提现、税务资料不足。

**外部证据：**
- PBOC 2021 通知页仍是中国虚拟货币监管基准之一；公开报道概括为虚拟货币相关业务活动受到严格禁止/限制，衍生品交易尤其高风险。
- Binance API 官方 FAQ 要求创建 API 前完成身份验证，交易/提现等权限与 IP 限制、安全控制绑定；无 IP 限制的系统 API key 默认只能读，提现权限必须 IP 限制。
- Binance API FAQ 还显示 API 可读取钱包/交易数据、交易、存取款，说明 key 权限错误会直接变成资金安全问题。

来源：PBOC 2021 notice page（`pbc.gov.cn`）；Binance API key FAQ（last updated 2025-03-20）：`https://www.binance.com/en/support/faq/detail/360002502072`；Binance Terms/Risk pages：`https://www.binance.com/en/terms`、`https://www.binance.com/en/risk-warning`。

**更优方案：上线前合规/对手方底线**

1. 写 `COUNTERPARTY_AND_COMPLIANCE_REGISTER.md`：交易所实体、服务地区、KYC 状态、可用产品、出入金路径、提现限制、税务资料导出能力、应急联系人。
2. 资金安全：交易所只放运行额度；利润每月或达到阈值回撤离线；核心资本不在交易所。
3. 对手方分散：研究/采集可多所；小额实盘执行可先单所，但当交易所余额 > 总本金 40% 或 > 10,000 元时，必须评估第二通道或降余额。
4. 稳定币风险：USDT 脱锚/提现暂停/链拥堵写入事件风控；不是只在 carry 回测里处理。
5. API key：独立 key、只交易不提现、IP 白名单、定期轮换、密钥不落仓库、不进报告、不进日志。
6. 中国税务/合规：实盘前请合格税务/法律顾问给一页书面意见；项目内部最低要求是保留完整交易、出入金、汇率、费用、平台 statement。

**谁决策：** Founder D 级确认是否承担该法域风险；Claude 提交登记册；Codex 实现密钥和归档控制。

### 6. 重大：运营“无人负责”仍未闭环，Founder 30 分钟/日假设过乐观

**问题：** 文档假设 Founder 日常只看报告，但 Phase 2 真正缺的是谁接告警、谁判断停机、谁复账、谁恢复。当前 Claude 是 Accountable，但没有运行时 on-call 机制，也没有 Runbook、告警分级、恢复演练。自动交易不是“无人值守”，而是“机器先止血，人按 Runbook 接管”。

**证据：**
- 总图 §5.1 明确 Phase 2 日常运行接口无人负责。
- `PROJECT_TASK_PLAN.md`：P1-OPS-001~005 大多新增/待办。
- `PHASE2_SYSTEM_BLUEPRINT.md`：Founder 日常目标 ≤30 分钟/天，但具体告警接管链仍是草图。

**更优方案：最小可行运营（MVO）**

1. 告警分级：
   - P0：未对账持仓、交易所持仓存在但 DB 无、API key 异常、强平/ADL、账户冻结、提现暂停、NAV 差异。
   - P1：数据停更、订单失败、风险扫描超时、AI worker 连续失败、日亏预警。
   - P2：日报缺失、非关键数据延迟。
2. 接管规则：
   - P0 自动禁止新开仓；必要时只允许 reduce-only；立即通知 Founder + Claude。
   - P1 禁止新开仓或降频，Claude 当日处理。
   - P2 记录并在日报中处理。
3. 每日闭环：
   - UTC 日结生成 NAV、持仓、订单、funding、fee、PnL 分解。
   - Founder 只看“是否需 D 级动作”，不做技术判断。
4. 演练门：
   - 每月一次 kill switch、重启恢复、交易所对账差异、API timeout、数据停更演练。
5. 记录：
   - 每个告警必须有关联 Runbook、owner、状态、处置时间、复发防护。

**谁决策：** CTO 定义运营制度；Codex 实现告警/日结；Founder 只批 P0 资金动作。

### 7. 一般但必须冻结：Track B AI 权限边界正确，但“no_trade 建议”不能演化成隐性 veto

**问题：** DEC-071 和 E2 已正确规定 AI Pre-Execution Analyst 不下单、不改仓位、不绕过 Gateway。但设计里仍出现 `approve/caution/no_trade/needs_human_review` 这类语义，未来容易被运营层误读成 AI 有交易裁决权。

**证据：**
- DEC-071：AI 不下单、不改仓位、不绕过 Gateway。
- `02_SYSTEM_ARCHITECTURE.md`：v1 advisory/audit layer，不是 veto gate；unavailable 不能伪装 approve。

**更优方案：**
- AI 输出字段改名为 `advisory_label`，禁止命名为 `decision`、`approval`。
- Gateway 决策表完全不读取 AI 文本；最多读取已白名单的结构化 `risk_annotation`，且默认不影响交易。
- 若未来要 AI veto，必须新 DEC、新预登记式验收、新故障注入，不得在 v1 偷渡。

**谁决策：** CTO 可决策；涉及自动 veto 时 Founder D 级。

## 四、致命盲点

项目一直把“策略能不能赚钱”审得很严，但对“钱能不能安全地待在系统里”审得不够硬。

真正的归零路径是：

1. 小额上线被当作低风险；
2. 交易所账户/API/cross margin 没隔离；
3. Gateway/对账/告警还没代码；
4. 某次 API、账户冻结、数据停更、部分成交或强平后裸露发生；
5. Founder 不在线，Claude 没有运行态接管工具；
6. 事故从围栏账户穿透到核心资本或造成账务不可解释。

这不是理论风险。项目历史 Ghost Position 已经演示过“状态源错误 + 无对账”如何让持仓消失于风控之外。下一次如果发生在真实资金、永续、交易所账户和 API key 上，损失机制会更快。

## 五、总判定

两层资本、证据等级解锁、杠杆=输出、认亏定仓这些原则是对的；3 万本金上限也合理。但当前缺的是把原则变成不可绕过的机器约束、账户边界和运营责任。

**上线判定：**
- paper/shadow：可继续推进，但必须同步补 MVR/MVO/ledger。
- 小额真金：当前 NO-GO。
- 核心资本：当前 NO-GO，且即便未来 PASS，也不应把核心资本主体放交易所。

**更优总方案：** 不再讨论“先 1000 元试试”。改成“先用 paper 把信号到结算、异常到恢复、绩效到账务跑通；再用最小真实资金只验证真实成交/出入金/交易所 statement；最后才谈策略实盘表现”。
