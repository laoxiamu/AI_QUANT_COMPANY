# AUDIT-2026-06-15-A2：系统架构 + 工程 + 数据基础设施审计

**棱镜：** 要建的东西对不对、能不能可靠跑起来  
**审计员：** Codex / AUDIT-A2  
**独立性声明：** 按 `04_AI_TEAM/CODEX_TASKS/AUDIT_CHARTER.md` 执行；不读取 Holdout；不参考其他棱镜结论；只写本报告和 TASK_INBOX 完成事件。  
**总判定：** 当前 Phase 2 方向的安全原则是对的，但实现路线仍偏“蓝图完整、运行证据不足”。对 3 万本金 / 单 Founder，真正过度设计的不是 PostgreSQL 或 Decision Gateway，而是过早建设 Track B AI 分析层、全量五层命名体系和持续扩张治理文档；真正建设不足的是数据合同、对账账本、故障恢复、第三方数据策略和执行引擎复用决策。

## 一句话结论

**立即改：** Phase 2 必须先降级为“最小 paper 交易内核”：数据合同 + 单一账本 + paper exchange + Decision Gateway + 对账/恢复演练。Track B AI、日报 UI、多策略扩展、完整生产化监控都应后移。  
**下阶段改：** 用 3-5 天做 NautilusTrader / Freqtrade / 自建薄内核对照 spike，不能在没有对照证据时默认自建执行系统。  
**记录待议：** 真实数据源策略要从“自建采集器优先”改为“官方 REST/WS + 第三方历史源 + 自采前向源三层校验”，否则数据质量会成为比策略本身更大的亏钱来源。

## 发现 1：Phase 2 蓝图方向基本正确，但右量级应收缩为“三模块内核”而不是五层全量生产系统

- **严重度：重大**
- **问题：** Track A 五层 + Track B AI 分析的概念方向合理，但对当前 3 万本金、1 Founder、尚无可部署 edge 的状态，完整五层建设会把资源消耗在命名和周边能力上。当前必须建设的是最小可验收运行内核，而不是完整交易公司平台。
- **证据：**
  - `COMPANY_BUILD_MASTERPLAN_v1.md` 将交易平台、实时风控、账务列为“草图”，运营监控列为“空白”。
  - `PROJECT_TASK_PLAN.md` 的 `P1-PLAT-003~010`、`P1-RISK-002~006`、`P1-OPS-001~005`、`P1-ACC-001~005` 均未完成。
  - `05_TECH_DESIGN/02_SYSTEM_ARCHITECTURE.md` 目前仍是 DRAFT，且 Layer 1-4 大多“待 Phase 2”。
- **更优方案：** Phase 2 改成三个深 Module：
  1. **Market Data Contract**：价格源、funding、OI、强平、时间戳、缺失、hash、freshness 的单一验收 Interface。
  2. **Trading Ledger Kernel**：PostgreSQL schema、order/trade/position/cash/funding/NAV、idempotency、reconciliation、restart recovery。
  3. **Deterministic Strategy Adapter**：策略只输出不可变 decision request，Decision Gateway 只消费该 request。
- **谁决策：** CTO 可重排；若改变 Phase 1→2 门槛，由 Founder D 级确认。

## 发现 2：PostgreSQL 唯一权威不是过度设计，是事故后最低安全门槛

- **严重度：重大**
- **问题：** 对小资金而言 PostgreSQL 看似重，但本项目历史事故恰好证明“内存状态 + 弱唯一标识”会直接产生未检查持仓。这里的过度设计不在 DB，而在没有先冻结 DB Interface 就画上层模块。
- **证据：**
  - `PROJECT_CONTEXT.md` PC-02：ETH 多头因内存字典覆盖从风控检查中消失约 1 小时，实际亏损 -5.47%。
  - DEC-008~011 已确认 PostgreSQL 权威、trade_id、Reconciliation Loop、Orphan Detection。
  - `PROJECT_TASK_PLAN.md` 中 DB schema、trade_id、状态机、恢复、对账仍是待办。
- **更优方案：** 坚持 PostgreSQL，但只建单机最小 schema + migration + WAL/每日 dump + `pg_restore` 演练；不要上分布式、复杂队列、Grafana 大盘。SQLite 不建议作为交易状态权威，除非仅用于离线回放。
- **谁决策：** CTO 自动执行；Founder 不应被问数据库选型。

## 发现 3：Decision Gateway 必须自建薄层，但交易所连接、订单重试和执行语义不应全部手写

- **严重度：重大**
- **问题：** Gateway 作为风险裁决 seam 必须归项目控制，但底层 exchange adapter、订单状态追踪、重试、限速、dry-run/live 切换若全自建，会重复踩成熟框架已经解决的坑。
- **证据：**
  - DEC-056/061 明确“先借鉴后重造”，但 `PHASE2_SYSTEM_BLUEPRINT.md` 仍写 `python-binance SDK` + 自建订单管理，缺少对 Nautilus/Freqtrade 的实证对照。
  - `PROJECT_TASK_PLAN.md` 已计划 `P1-PLAT-009` paper 订单执行器与幂等重试，但尚未规定是否复用框架。
  - NautilusTrader 官方定位为研究、确定性仿真、实盘同一事件驱动架构；Freqtrade 已有 dry-run/live、交易所支持、Telegram/WebUI 和 SQL 历史。
- **更优方案：**
  - 先做 spike：同一个 carry 简化策略，在 NautilusTrader、Freqtrade、自建薄内核各实现最小 replay/paper 流，比较 5 项：spot-perp carry 表达能力、账务可解释性、Binance USD-M 支持、DB/ledger 可控性、运维复杂度。
  - 若 carry 的 cross-margin / spot-perp ledger 让 Freqtrade 难适配，则 Freqtrade 只作运营/监控参考，不作核心。
  - 若 NautilusTrader 能表达策略和账本，优先采用其执行/回放内核，把项目自建范围限制在 Strategy Adapter、Gateway policy、PostgreSQL audit projection。
- **谁决策：** CTO；若引入重依赖改变 Phase 2 架构，Founder D 级确认。

## 发现 4：Track B AI Pre-Execution Analyst 现在是右方向、错时机

- **严重度：一般到重大**
- **问题：** Track B 与 Track A 隔离是正确的，但当前没有实盘策略、没有权威账本、没有对账和告警。先做 AI 执行前分析会增加异步 worker、schema、timeout、成本、误读告警和解释负担，降低 Locality。
- **证据：**
  - `05_TECH_DESIGN/02_SYSTEM_ARCHITECTURE.md` 已详细定义 AI Worker、schema、timeout、cap、circuit breaker。
  - `PROJECT_TASK_PLAN.md` 的 `P2-AI-001~003` 依赖平台、账务和监控数据；这些前置均未完成。
- **更优方案：** Track B 保留设计，不进入 Phase 1 最小平台。第一版只产出离线日报脚本，从 PostgreSQL snapshot 读取并写 Markdown，不参与执行前路径。AI Pre-Execution Analyst 等 paper 平台 14 天零差异后再接。
- **谁决策：** CTO 可调整；Founder 只确认 Track B 是否仍为 advisory。

## 发现 5：数据质量和基建可靠性是项目隐藏最大风险，且已多次实际暴露

- **严重度：致命**
- **问题：** 当前最可能让实盘亏钱的不是策略公式，而是“数据看起来有、实际不适用”：contract vs mark klines 混用、base volume 被当 quote volume、funding 缺失、WS 旧路由 0 帧、service active 被误当业务健康。
- **证据：**
  - `REPORT_D2.md` 因 `PRICE_SOURCE_MISMATCH`、`MISSING_REAL_FUNDING`、`DEC_070_FILTERS_NOT_AUDITABLE` 阻断。
  - `REPORT_DEC070_AUDIT.md` 显示 35/35 CSV 无精确 quote volume，float market cap 和 OI/market cap 本地不可算。
  - `REPORT_FIX_COLLECTOR_URL.md` 显示采集器 2026-06-13 至 2026-06-14 heartbeat 均为 `process_messages=0`，但服务仍 active。
  - Binance 官方文档说明 2026-04-23 后 legacy `/ws` 不再推送 market/private 类流，`!forceOrder@arr` 属 `/market`。
- **更优方案：**
  - 建 `DATA_CONTRACT.yaml`，每个数据集必须声明 source、endpoint、price_type、volume_type、timezone、cutoff、funding timing、schema hash、freshness SLO、缺失处理、可替代源。
  - 任何研究或 paper 策略入口先跑 `data_contract_check.py`，失败即不运行策略。
  - 强制业务健康标准：不看 `systemctl active`，只看 last_message_age、row_delta、heartbeat_count、schema_version、sample parse success。
- **谁决策：** CTO 自动；数据供应商付费超过月预算需 Founder D 级。

## 发现 6：A-1 前向强平数据被称为“真实强平名义额”仍有口径盲点

- **严重度：重大**
- **问题：** Binance 全市场强平流不是逐笔全量流；官方说明每个 symbol 每 1000ms 只推最大一笔强平 snapshot。因此自采 `!forceOrder@arr` 适合作为前向压力代理，不应写成完整市场强平名义额。
- **证据：**
  - Binance 官方 `All Market Liquidation Order Streams` 文档：每 symbol 每 1000ms 只推最大一笔 liquidation order；无强平则不推。
  - `A1_FORWARD_LIQUIDATION_PATH.md` 与当前状态把采集器作为 A-1 路径 B 的 alpha 用途，但数据合同未显式写 snapshot 抽样偏差。
- **更优方案：** A-1 路径 B 改名为“Binance forceOrder snapshot proxy”。所有阈值和功效门基于 snapshot notional，不声称全量强平。若要全量/更完整历史，采购 Tardis.dev/Kaiko/Coin Metrics 类历史衍生品数据做交叉验证。
- **谁决策：** CTO；若采购数据源由 Founder D 级。

## 发现 7：第三方历史数据应进入主路线，不应只在自建失败后补救

- **严重度：重大**
- **问题：** 当前数据策略偏“官方 API + 自采”，这对前向收数便宜，但对历史验证、缺失回补、schema 变更追踪不足。D2 和 DEC070 已证明本地历史源不足会阻断研究。
- **证据：**
  - `REPORT_DEC070_AUDIT.md`：OI/market cap 历史窗口不可从 Binance 近端 REST 回补。
  - `PROJECT_TASK_PLAN.md` 尚无供应商数据试用/成本/字段验收任务。
  - Tardis.dev 官方文档提供 exchange-native 历史 WS 数据、liquidations、derivative_ticker、trades 等；对强平和衍生品历史尤其相关。
- **更优方案：** 建 1 个小任务：对 BTC/ETH/SOL、2024 年 1 个月采购或试用第三方数据，验收字段、延迟、费用、许可证、hash、与 Binance 官方 REST/WS 的一致性。通过后，关键研究用第三方历史源交叉校验，自采只做前向补充。
- **谁决策：** CTO 做试用技术验收；付费由 Founder D 级。

## 发现 8：工程实践在研究层合格，但生产层测试类型缺失

- **严重度：重大**
- **问题：** 研究代码已有 pytest、seed、报告三件套、专业异议，质量明显进步；但交易生产层需要的是状态机、幂等、崩溃恢复、对账、时钟错乱、网络分区、重复成交等故障注入测试，目前还没形成。
- **证据：**
  - `REPORT_CARRY_SCAFFOLD.md` 有 25 项合成测试；`REPORT_A1_TIERA_EXEC.md` 有固定 seed 和权限负测；说明研究层纪律可运行。
  - `P1-RISK-006`、`P1-OPS-005`、`P1-ACC-003` 仍是待办。
- **更优方案：** 在任何真实资金前，必须有 `paper_failure_tests/`，覆盖：重复下单、订单部分成交、撤单未知、DB 写失败、进程重启、交易所状态与 DB 不一致、funding 到账延迟、mark/index 缺失、WS 零帧、API 429、机器断网。
- **谁决策：** CTO 自动。

## 发现 9：平台抽离在文档里做到了，在代码里尚未做到

- **严重度：重大**
- **问题：** SOP 已明确单策略不能重复建设订单/状态/风控/监控/账务，这是对的；但仓库当前仍主要是研究脚本集合，`06_RESEARCH/CODE` 中多处策略脚本各自定义 Position、funding、成本、equity。若直接进入循环 E，重复建设风险会复发。
- **证据：**
  - `OPERATING_MODEL_DESIGN_v2.md` 明确循环 E 前提是已有最小交易平台，不得由某策略从零建设交易系统。
  - `PROJECT_TASK_PLAN.md` 的 `P1-PROD-007` 明确“不建立策略私有订单/状态/账务旁路”，但处于待办。
  - 代码搜索显示多个研究脚本内各自实现 `Position`、`funding_cost`、`positions: dict` 等研究级状态。
- **更优方案：** 在 carry 若 PASS 后，不允许先写 carry runner。先写平台 Interface：`decision_request`、`ledger_event`、`position_snapshot`、`risk_check_result`。carry 只实现 Adapter，不能写私有账本。
- **谁决策：** CTO；Codex 执行时可自动拒绝违反范围的任务书。

## 发现 10：网络/运行基础设施不该再靠双跳代理和手工 SSH 作为关键路径

- **严重度：重大**
- **问题：** 双跳代理、VM 下载失败、DC 断联、旧 WS 路由误判，说明当前基建可用于研究跑批，但不适合作为交易运行依赖。换住宅 IP 不是根解；根解是减少对代理链的关键依赖，并把数据/交易通道分开验收。
- **证据：**
  - `CURRENT_STATE.md` 记录 downloads.claude.ai 双跳下载失败、DC 频繁断联。
  - `REPORT_VERIFY_V462.md` 证明 SG 直连 Binance REST 可用，WS 问题是路由迁移而非 IP 封锁。
  - `REPORT_FIX_COLLECTOR_URL.md` 证明最小修复是 WS URL，不需要住宅代理。
- **更优方案：**
  - 不建议现在换“非云住宅 IP”作为主方案；它增加不可控性、合规和维护成本。
  - 生产 paper/live 用一台稳定云 VM + 官方端点 + 健康探针；模型/下载流量与交易/数据流量隔离。
  - 只有当交易所明确限制云 IP 的某个必须端点，才增加第二出口，且要把出口选择写入数据合同。
- **谁决策：** CTO 自动；新增服务器或住宅代理费用由 Founder D 级。

## 哪些模块根本不该自己写

- **不该自写：** 通用回测优化框架、交易所原始连接和低层重试、历史 tick/强平/盘口数据归档、UI/移动端、多交易所抽象、机器学习超参搜索、AI 实时交易裁决。
- **可借鉴/采用：**
  - **VectorBT：** 适合研究扫描和快速向量化原型，不适合作为 live 执行权威。
  - **Freqtrade：** 适合单交易所 crypto bot、dry-run/live、运营监控参考；carry spot-perp 复杂账本可能不贴合，需 spike 验证。
  - **NautilusTrader：** 最值得 spike 的生产级候选，优势是研究到实盘语义一致；风险是学习成本和与项目自定义账本/Gateway 的整合成本。
  - **官方 SDK / connectors：** 可作 exchange adapter 的底层，但必须包在项目自有 idempotency 和 audit projection 之后。
- **必须自写但要小：** 研究统计校验函数、数据合同检查、Gateway policy、账务恒等式断言、策略 Adapter、项目特有审计报告。

## 致命盲点

实盘前最可能出事故的缺陷是：**数据源或状态源看似健康但业务语义错误，导致 Gateway 用错误 mark/funding/OI/position 做正确形式的错误决策。**

最危险路径示例：

1. 采集器 service active 但 0 帧，A-1/OI 风险暂停未触发。
2. contract kline 与 mark price 混用，强平/保证金检查低估风险。
3. funding timestamp 或数量归属错，carry NAV 虚高。
4. DB 与交易所持仓不一致，runtime 仍继续下单。
5. Track B AI 基于过期 snapshot 给出看似合理解释，掩盖数据新鲜度事故。
