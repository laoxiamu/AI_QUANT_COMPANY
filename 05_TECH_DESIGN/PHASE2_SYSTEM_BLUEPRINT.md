## 一、系统定位

**目标：** 把 Phase 1 验证的 edge（TSMOM扩展版 / A-1级联回弹 / Carry sleeve）翻译成能 24 小时自动运行、Founder 每天只看报告的生产级交易系统。

**运行环境：** 腾讯云 SG 服务器（43.160.200.224，2核/4GB/60GB）+ 本地 Mac 作为管理端

**不建设的东西：**
- 不造 UI 和 App（CLI + 每日报告足够）
- 不引入 RL/自进化（Phase 2 阶段不需要，加复杂度不加价值）
- 不多交易所（先只做 Binance，成熟后再扩）

## 二、架构层次（双轨制）

```
                    ┌─────────────────────────────────┐
                    │  Track B: AI主动分析轨道          │
                    │  Claude日报/周报/异常分析/月度评估 │
                    │  主动输出判断，不等Founder来问     │
                    └────────────┬────────────────────┘
                                 │ 读取数据（只读）
┌────────────────────────────────▼────────────────────┐
│  Layer 4: 监控与报告层（Track A）                     │
│  结构化日志 / 告警推送 / 数据快照（供Track B读取）     │
├─────────────────────────────────────────────────────┤
│  Layer 3: 决策与风控层（Decision Gateway）            │
│  信号聚合 / 仓位计算 / 硬熔断 / 最终裁决             │
├─────────────────────────────────────────────────────┤
│  Layer 2: 策略层                                     │
│  TSMOM信号 / A-1事件检测 / Carry状态 /               │
│  Regime分类器 / 强平压力监测                          │
├─────────────────────────────────────────────────────┤
│  Layer 1: 数据与执行层                               │
│  Binance API / 行情采集 / 强平采集器 /               │
│  PostgreSQL（唯一真实源）/ 订单执行                   │
└─────────────────────────────────────────────────────┘
```

Track A（4层）：全自动，毫秒级，无AI在执行路径。
Track B（AI分析）：Claude定期主动读取Track A数据输出分析。两轨完全分离，Track B故障不影响Track A执行。

## 三、六条工程铁律（独立推导，非"继承V4"）

这六条是从"任何24小时无人值守量化系统的生存条件"独立推导出来的。V4后期也确立了这些原则，但这里引用是因为内容正确，不是因为它们来自V4。

1. **单向控制流**：策略层只产生信号，Decision Gateway 唯一有权下单。策略不能直接调用交易 API。
2. **Risk-First**：任何下单请求必须经过 Decision Gateway 校验，风控规则硬编码，不可被策略覆盖。
3. **唯一真实数据源**：PostgreSQL 是所有模块的状态权威，内存变量只作缓存，风控决策不依赖内存状态。
4. **可审计**：所有决策链路写日志，每笔交易可追溯到触发的信号和通过的风控检查项。
5. **先可靠再盈利**：系统 Risk Integrity（持仓同步/熔断可靠/重启恢复）必须先验证，才开始实盘。
6. **AI 分析独立于执行链路**：Claude 主动分析运行在 Track B（周期性），不在 Track A（毫秒级执行路径）里。AI 的主观判断能力通过定期分析实现，不通过实时控制交易实现。

## 四、策略层设计（Phase 1 研究产出映射）

### 4.1 TSMOM 策略模块（主方向，Phase 1 验证中）
- **输入**：Tier 1 universe（~20-30 个资产）4H OHLCV
- **信号**：regime gate + 动量方向
- **仓位**：Risk Parity（继承 V4 B'1：1/ATR% + 相关性惩罚 × 0.6）
- **上线条件**：D2 回测通过四件套 + 第五件

### 4.2 Carry 策略模块（sleeve，Phase 1 实证完成）
- **资产**：BTC 70% / ETH 30%（1x long spot + 1x short perp，无杠杆）
- **收入**：每 8h 收取 funding rate
- **暂停信号**：A-1 触发（OI 骤降 P1 分位）→ 临时退出 carry，待稳定后重建
- **上线条件**：carry 预登记通过 + A-1×Carry 交互逻辑验证

### 4.3 A-1 事件检测模块（辅助 + 未来独立策略）
- **功能**：实时监测 OI 骤降事件，双重用途：① 作为 carry 暂停信号；② 未来作为独立事件研究策略
- **数据源**：已有强平采集器 + OI 实时数据
- **上线条件**：A-1 预登记通过四门验收

## 五、Decision Gateway 规格（风控硬编码）

以下规则 **硬编码**，策略层不可覆盖：

| 规则 | 参数 | 来源 |
|---|---|---|
| 单日最大亏损 | 核心资本 -2% 熔断 | DEC-015/063 |
| 最大总回撤 | -20% 触发人工介入 | DEC-069 |
| 单资产最大权重 | TSMOM: 1/n_active，carry: BTC≤15%/ETH≤10% | DEC-070 + 本设计 |
| 事件窗禁交易 | CPI/FOMC/NFP 前后 ±1h | V4 B1 |
| 极端波动熔断 | 5min 价格跳动 >3% 暂停新建仓 | V4 B'2 |
| 强平级联检测 | OI 骤降 P1 → carry 退出 + 新建仓暂停 | A-1×Carry |
| 持仓同步验证 | 每 1h 比对本地持仓与交易所持仓，不一致告警 | V4 Ghost Position 教训 |

## 六、数据层与执行层

### 数据源（已有或已规划）
- **行情 OHLCV**：Binance API 实时拉取（现有数据 + 增量）
- **OI / Metrics**：Binance futures metrics API
- **强平数据**：`aiquant-liq-collector.service`（已部署运行）
- **资金费率**：Binance funding rate API（每 8h）
- **状态存储**：PostgreSQL（复用 V4 的设计原则，重新建库）

### 执行层
- **订单管理**：python-binance SDK，限价单优先，市价单只用于熔断平仓
- **重连/重试**：指数退避，最大 3 次，失败告警
- **重启恢复**：启动时先从 PostgreSQL 拉当前持仓，与交易所比对，不一致人工介入

## 七、双轨制架构（Track A 自动执行 + Track B AI主动分析）

**这是对 "想要一个活的系统，不是死的系统" 的具体回答。**

### Track A：全自动执行轨道（无AI，毫秒级）
```
数据采集 → 信号计算 → Decision Gateway风控 → 订单执行 → 状态写入PostgreSQL
```
特点：规则硬编码，熔断可靠，不等任何人，24小时运行。

### Track B：AI主动分析轨道（Claude定期主动输出，不等被问）

| 频率 | 触发条件 | Claude 输出内容 |
|---|---|---|
| 每日 | 定时（每天固定时间） | 主理人日报：不只报数字，要报"信号是否如预期、市场状态判断、下一步预警" |
| 每周 | 定时 | 深度回归：P&L归因（信号贡献 vs 市场beta）、策略是否偏移出预登记范围 |
| 异常触发 | A-1事件 / 熔断 / 回撤>1% | 事件分析：发生了什么、为什么、建议的响应（需Founder确认才执行） |
| 每月 | 定时 | 机会地图重新评估：主动判断是否需要调整研究方向，不等Founder发现 |

**Track B 的AI能力**：不是AI决定交易，而是AI持续主动"看数据、做判断、输出有观点的分析"。这是让系统"活"的方法。

### 每日自动报告格式（Track B 日报）
```
【主理人日报】2026-06-XX
持仓：BTC long 0.1 (carry) / TSMOM: ETH long 0.05, DOT long 0.03
今日P&L: +¥XXX / 累计P&L: +¥XXXX / 资金费率收入: +¥XX

【主理人判断】
- 信号表现：TSMOM信号本周触发3次，其中2次顺势（符合预期），1次逆势但未超止损
- 市场状态：BTC处于4H上行Regime，carry暂无A-1预警信号
- 预警：ETH funding rate本周出现1次负值，需关注是否触发A-1×Carry暂停条件
- 无需Founder干预

风控状态: 正常 / 告警: 无
```

### 异常触发告警（实时，Track A 产生，Claude 自动分析）
- 持仓同步失败 → 立即告警（规则触发，无需AI）
- 单日亏损 >1%（预警）/ >2%（熔断）
- OI骤降P1触发 → Claude自动生成事件分析，推送给Founder

## 八、运营工作流设计（Founder 视角）

**实盘后 Founder 的日常（目标 ≤30 分钟/天）：**

1. 早上：看每日报告（2 分钟）
2. 有告警：读告警描述，判断是否需要人工介入（D 级）
3. 每周：Claude 发来周审报告，读摘要，有问题回复（15 分钟）
4. 有重大策略问题：Claude 主动发起 D 级讨论，你拍板

**Founder 不需要做的：**
- 不需要盯盘
- 不需要手动下单
- 不需要写代码
- 不需要每次都跟 Claude 对话（只在有问题时）

## 十、与历史版本的关系（独立评估，非直接继承）

**V5分析结论（2026-06-13，读完原始文件后）：**
V5（ChatGPT 2026-05-08方案）的核心方向是：SMC结构行为（Liquidity/FVG/CHoCH）→证明单一Setup具备正期望。这条路线我们已经实验证伪（IC≈50%，A-2失败，SMC封存）。V5代表我们已经超越的失败路径，不应作为Phase 2设计参考。当前研究范式（机制优先+统计预登记+TSMOM/Carry/A-1）比V5更先进，不是更保守。

**与V4架构原则的关系（独立推导，不是"继承"）：**

| 组件 | 独立评估结论 | 与V4关系 |
|---|---|---|
| 单向控制流 / Risk-First / 单一真实源 | 任何无人值守量化系统的必要特征，独立推导得出 | V4也有这些，重叠 |
| Risk Parity 仓位（1/ATR%+相关性惩罚） | 合理启发式，TSMOM适用 | V4有，评估后采用 |
| "不做"条件清单（事件窗禁交易等） | 实战积累的有效规则，独立验证后纳入 | V4有，评估后采用 |
| PostgreSQL 单一真实源 | 行业标准最佳实践，独立推导 | V4也有，重叠 |
| AI-native Track B 分析层 | **V4没有，新设计** | 独立设计 |
